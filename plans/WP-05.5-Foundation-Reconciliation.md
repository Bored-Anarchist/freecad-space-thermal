## 1. Why this package is needed

The [FEM reuse decision](../docs/decisions/0003-freecad-fem-reuse.md) identified six candidate groups but assigned most evaluation to WP-13/WP-16. Some decisions affect already-frozen contracts, persistence, dependency manifests and test infrastructure. Deferring all of them until GUI or spatial implementation risks replacing useful FEM infrastructure, changing storage under active consumers, or presenting fields with ambiguous engineering meaning.

The following are observed baseline limits, not assertions that the completed packages failed their declared acceptance:

| Origin | Existing foundation | Missing handoff work owned here |
|---|---|---|
| WP-01 | Acquired vendor-example inventory with source hashes, rights dispositions and assigned gaps | Separate inventory of reusable FEM components and suitable synthetic upstream examples; provenance and license decisions for any adopted content |
| WP-02 | Basic FreeCAD/Part document and geometry smoke; standalone build and packaging probes | Actual pinned FEM API probes; selected mesher/import/export feasibility; dependency/license and clean-install evidence for the selected host path |
| WP-03 | Distinct faces/facets/elements/nodes, SI quantities, weighted maps, frames and typed result records | Explicit element-order/connectivity conventions and supported spatial subset; field association and vector heat-flux semantics; versioned extensions and migration/read rules |
| WP-04 | Independently checked network/CVODE prototype and sealed numerical evidence | Spatial oracle and comparison manifests usable by WP-16, with defined sample locations, units, refinement policy and independent expected values |
| WP-05 | Strict ZIP/HDF5/SQLite persistence, immutable imports, transactions and synthetic host coordination | Storage of the accepted extended fields/mappings; compatibility and corruption tests; representative real FEM document coordination probes |

The current result JSON enumerates `temperature`, `power` and `residual`; HDF5 v1 stores these as node-indexed scalar arrays. It does not provide a vector heat-flux field or a general field-location contract. The element record enumerates topology but has no explicit higher-order element descriptor. These are concrete contract decisions to resolve, not permission to inject unknown fields into v1. See [the contract bundle](../spec/contracts/README.md) and [HDF5 v1](../spec/contracts/hdf5-v1.json).

WP-01 through WP-05 remain complete for their recorded baselines. Preserve their original evidence, fixture hashes and failed/superseded attempts. WP-05.5 completion requires new supplemental evidence for changed sources/contracts. This document and a green planning check do not qualify FEM integration or implement the outstanding work.

## 2. Scope and sequencing

Deliver these foundation outputs in order: inventory and supported subset; pinned API/mesher prototypes; contract/version decision; independent conformance/oracle fixtures; storage and host-boundary implementation; integrated verification and handoff. A contract may be drafted alongside the API probes, but freeze its criteria and supported semantics before implementation results are assessed.

Add WP-05.5 as a direct prerequisite of WP-06, WP-07, WP-13 and WP-16. They may scaffold against unchanged interfaces while this package runs; acceptance of dependent contract/result/host/mesh behavior requires the completed handoff. WP-05.5 depends only on WP-01 through WP-05: it must not depend on the production GUI, worker scheduler or FE solver it is preparing. Use small isolated probes and synthetic values where those products do not exist yet.

Keep these later obligations with their existing owners:

- WP-06 implements durable jobs, cancellation and atomic worker result publication.
- WP-11/WP-12 implement production thermal assembly, solving and coupled spacecraft radiation.
- WP-13 implements the full workbench, editors, asynchronous interaction and displayed engineering workflows.
- WP-16 implements and qualifies production spatial formulations, contacts, material behavior and mesh refinement.
- WP-19 qualifies the complete product, distribution and selected comparison profiles.

The six FEM-REUSE cases remain the later feature acceptance IDs. WP-05.5 supplies their prerequisites and representative contract/host probes; it cannot mark those later cases passed. Optional external references must not become a requirement for geometry-free native development. An unavailable selected reference blocks its comparison profile and remains explicitly unqualified.

## 3. Detailed workstreams and deliverables

### A. Component and example inventory — WP-01 follow-up

1. Inventory all six FEM candidate groups: analysis/document objects; mesh objects/I/O and meshing integration; materials/selections/thermal load tools; result objects/pipelines; examples/test patterns; CalculiX/Elmer reference interfaces.
2. For each candidate, record exact source URL/path/revision and content hash, public symbols, runtime dependencies, per-file license/notice hashes, intended consuming component and disposition: reuse API, adapt source, replace or defer. Record technical limits, maintenance/deployment effort and measured prototype evidence. Replacement needs a specific failed requirement or incompatibility plus smaller reuse alternatives considered.
3. Select synthetic fixtures that cover at least a geometry-free network, a simple solid mesh, a surface/facet mapping and a rotated material/field case. Record whether independently authored or adapted, upstream attribution, modification history, redistribution rights and privacy disposition. Public availability alone is not publication clearance.
4. Keep this inventory separate from the 55-file vendor-example inventory. Do not reclassify acquired originals, remove their holds, rewrite their bytes or imply a new compatibility qualification. Track unresolved reuse questions with owner, affected capability, planned test and blocking gate.

**Deliverables:** versioned reuse/source-license manifest; synthetic fixture manifest; complete candidate dispositions; safe attribution records. **Acceptance:** WP055-INV-001/002.

### B. Pinned FEM and mesher feasibility — WP-02 follow-up

1. Probe actual candidate APIs using the pinned official Windows FreeCAD bundle and its embedded Python. Record host asset/source hashes, Python/Qt/OCCT/FEM versions or source identities, imported symbols and selected dependencies. Do not substitute a weekly host or replace embedded Python to obtain a passing result.
2. Create minimal document/analysis/mesh/result objects, exercise selection/reference access and check mesh topology/coordinates and field arrays. Run on the application thread under a supervisor with explicit timeouts and bounded diagnostics. The existing geometry smoke remains separately named and unchanged in its qualification claim.
3. Evaluate FEM mesh I/O and Gmsh/Netgen integration. Select at least one supported reproducible generation/import path for the declared subset, with exact executable/library build, license, options, element families, units, deterministic identity policy and offline installation requirements. An unevaluated second mesher is explicitly unsupported/deferred, not implicitly supported.
4. Test missing modules, incompatible ABI, changed/missing symbols, unavailable mesher and unsupported elements. Emit capability-specific failures; import success alone is insufficient. Keep optional mesher/solver discovery away from mandatory native engine startup.

**Deliverables:** isolated probe payload/supervisor; pinned selected profile and dependency records; bounded API/mesher results; clean-install instructions. **Acceptance:** WP055-HOST-001/002.

### C. Mesh, material and result contract reconciliation — WP-03 follow-up

1. Freeze a supported first implementation subset from measured host behavior and required model semantics. Name element topology, order, node ordering, orientation, local frame, thickness/volume/area meaning and index conventions. Identify unsupported shells, mixed-order cells, integration-point fields and higher-order elements explicitly. Reject them before solve/export rather than dropping midside nodes or inventing a reduction.
2. Define the association between mesh vertex IDs, element/facet IDs and thermal node UUIDs. Retain distinct CAD, conduction, radiation and thermal identities, including many-to-many weights/areas and provenance. Define mesh-generation/revision identity and replacement/refinement rules; ordering changes cannot silently remap loads or fields.
3. Define fields independently of a specific result viewer: physical quantity; scalar/vector/tensor rank; component ordering; unit/dimension; location such as thermal node, mesh vertex, element or facet; associated mesh/entity index; frame and transform; sample times; validity mask policy; and method/provenance for projection or averaging. Support only the declared subset, with explicit rejection for the rest.
4. Specify heat-flux vectors in W/m2 separately from integrated power in W. Freeze vector direction, local/global basis and outward-normal conventions; distinguish raw values from interpolated/extrapolated/averaged displays. Document checks for rotated fields and area-integrated boundary power. Absolute temperature and temperature differences retain their existing type rules.
5. Freeze source-material and boundary mappings: scalar versus oriented tensor conductivity, density/heat capacity, applied surface flux versus total power, prescribed temperatures and any supported time dependence. Preserve quantities and assumptions; do not import solver-deck-specific defaults as canonical truth.
6. Publish an architecture/version decision covering model/result/HDF5 versions, minimum readers, capabilities, compatibility matrix, canonicalization and migration. Determine minor versus major changes from the actual compatibility rules; do not assume a version number in advance. Keep released 1.0.0 fixtures and expected hashes intact. Old readers reject unsupported new content before mutation; new readers retain declared v1 compatibility. Lossy downgrade fails explicitly.
7. Update generators, generated schemas/enums/bundles, native and Python readers together. Independently authored positive/negative fixtures must prove normalized values, hashes and diagnostics agree. Separate normalized engineering meaning from exact artifact byte hashes and viewer state.

**Deliverables:** supported-subset and field/mapping specification; version/capability ADR; generated contract extension; compatibility fixtures and independent readers. **Acceptance:** WP055-CTR-001 through WP055-CTR-005.

### D. Spatial oracle and reference preparation — WP-04 follow-up

1. Prepare executable expected-value generators/manifests for a steady rod/slab, a transient conduction case, a rotated anisotropic manufactured field and a boundary-flux/total-power check. State equations, dimensions, geometry, material laws, boundary/initial conditions, sample locations/times and exact assumptions. Expected values must not come from the production code under test or a reused result-import path.
2. Freeze absolute/relative tolerances, normalization floors, energy measures, mesh/time refinement sequences and expected failure categories before results are run. Where a production FE solver is absent, verify analytic/manufactured values and field transformations with independent calculations and synthetic sampled fields; production convergence remains WP-16 acceptance.
3. Define a separately identified optional CalculiX/Elmer comparison profile: exact builds, supported thermal subset, matched inputs, node/cell sampling and projection, transient stepping, criteria and provenance. No need to select both. Record run mode as `reference_external`; no external temperature field can satisfy `fcst_native` evidence.
4. Retain the C++/SUNDIALS decision, reference hardware and sealed network baseline. A spatial failure opens its own defect/evidence attempt; it cannot be hidden by changing the prior network criteria or claiming that passing a network case proves spatial behavior.

**Deliverables:** independent spatial fixture/oracle manifests and runnable expected-value generators; predeclared refinement/comparison policy; selected/deferred external-reference dispositions. **Acceptance:** WP055-NUM-001/002.

### E. Array storage, compatibility and corruption boundaries — WP-05 follow-up

1. Implement the accepted extended result/mesh layout with explicit field association, UUID indexes, components, frames, units, times and provenance. Bind JSON declarations to actual HDF5 role, datasets, types/shapes, ordering and semantic/artifact hashes. A scalar power array cannot be accepted as a vector flux field.
2. Persist mapping/attachment/revision records and declared source/license references through ZIP/expanded package and fresh-process store reconstruction. Register actual dependencies so changes to geometry, connectivity, materials, loads and frames invalidate only the appropriate live data; historical results stay bound to their original snapshot and are visibly historical.
3. Implement the declared migration/read matrix. Check unchanged v1 reopen and hashes; new-format round trips; unknown major/minimum-reader failures; absent required fields; malformed associations; and unsupported downgrade without overwriting source or prior good revision. Keep migration code inert and trusted, not embedded executable package content.
4. Extend fault injection for write/flush/replace/journal/host synchronization and registration of the new arrays/maps. No partial array publication, mismatched result identity, stale clean host state or recalculated trust in corrupted originals is acceptable.
5. Preserve resource/security controls: preallocation limits, bounded actual reads, closed dataset/attribute vocabulary, safe codecs, traversal/link rejection, no external/virtual/filter-backed HDF5 storage, disabled plugin loading, dependency closure and retained original manifest pins. A new format must not silently relax existing checks.

**Deliverables:** extended array reader/writer and package/store validation; migrations/read matrix; compatibility, corruption and crash regressions. **Acceptance:** WP055-STORE-001 through WP055-STORE-004.

### F. Representative host transaction and result handoff

1. Implement a narrow FEM-to-canonical adapter probe using the existing application operation boundary. Create/edit/save/reopen/undo a synthetic host object/mesh with stable IDs and compare its canonical snapshot with the equivalent standalone operations. Never pass live host pointers across the worker boundary.
2. Exercise face reorder/split/merge/delete, mesh replacement and a material/frame/load edit. Preserve explicit reassignment for ambiguous attachments and invalidate dependent fields. Direct host changes mark dirty until reconciled. An apparent matching face signature is insufficient to adopt a new attachment automatically.
3. Bind the selected result object/pipeline to synthetic scalar/vector fields from the accepted storage contract. Assert actual data, units, frames and row IDs against canonical queries. Test stale-result refusal, supported projection metadata and save/reopen. Screenshots supplement data assertions and require separate privacy clearance.
4. Reproduce an interrupted host/package save and a competing update using the existing journal/locks. No false clean revision is allowed. These are automated foundation probes, not the full WP-13 GUI or WP-06 job lifecycle.

**Deliverables:** representative adapter/field mapping boundary and unattended host fixtures; documented handoff to FEM-REUSE-002/003/004/005. **Acceptance:** WP055-HOST-003/004.

Identical blob content under a different or restricted path cannot inherit an unsafe clearance. Deleted-history secrets and unapproved identities remain detectable. Record measured disposition even if no optimization is adopted; runtime alone never permits bypassing publication checks.

**Deliverables:** regression-to-finding ledger; bounded resource profile; owned issue dispositions; scanner cost/coverage assessment. **Acceptance:** WP055-AUDIT-001/002, WP055-TOOL-002 and WP055-PUB-002.

## 4. Executable acceptance and evidence rules

The [acceptance register](WP-05.5-acceptance.csv) names the required scenarios, owner roles, suites, requirement IDs, objective behavior and evidence. Implementers supply unattended commands with each feature; the user is never the test operator. Public tests use synthetic fixtures and no licensed/restricted engineering originals. Run host jobs under the pinned host environment and standalone/native tests under their separate environments.

Freeze each case's expected quantities, thresholds, failure diagnostics, supported profile and exact inputs before executing it. Retain the original result when criteria change. Unsupported optional profiles need explicit dispositions; an unavailable required host/mesher path or declared external comparison remains blocked. A replacement implementation must pass the same behavior assertions as reused infrastructure.

Engineering exit requires all acceptance rows implemented and passed on their applicable configurations, plus existing contract/numerical/persistence/privacy regression gates. Run both Windows debug/release drivers for changed native/application contracts; real host probes run on the pinned Windows desktop profile with watchdogs. Engine-only launch/dependency checks still prove no host/Python/external solver substitution. Spatial production solves and full GUI use remain later-package acceptance.

Use `python -S tools/check_security.py` for planted cases and `python tools/publication_preflight.py` for actual staged/revision/file bytes. Public reports contain bounded metrics, case IDs, approved source references and hashes; findings never echo matched sensitive values. Clear the final generated report immediately before CI upload. A source license or successful engineering test is not privacy clearance.

**Acceptance:** WP055-PUB-001/002 plus the existing TST-021 regressions. Scanning improvements must preserve fail-closed unsupported-media and archive/resource policies.
